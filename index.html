Overview

01 관리자의 작업 흐름을 이해하고, 화면부터 서버까지 개발합니다

인터엠에서 PHP와 JavaScript로 오디오 장치 관리 화면과 서버를 개발하며, 장치를 등록하고 건물 도면에서 제어할 대상을 골라 재생 파일과 실행 조건을 설정하는 기능을 구현했습니다. 설정을 마치면 서버가 해당 장치에 명령을 보내고 관리자는 화면에서 그 결과를 확인할 수 있습니다.

외부 시스템에서도 웹 관리 화면의 제품 설정과 조회 기능을 사용할 수 있도록 Interm API를 제공했으며, 관리 서버와 장치 사이의 통신은 내부 REST API로 연결했습니다. 한화향 제품에서는 외부 시스템이 SUNAPI로 장치 정보와 설정을 조회하는 기능을 담당했습니다.

02 저장 속도와 실패 상황까지 개발 범위로 보고 개선합니다

이벤트 설정을 한꺼번에 저장할 때 PHP가 행마다 SQL을 실행해 처리 시간이 길어져 여러 행을 한 번에 저장하는 방식으로 바꿨습니다. SQLite에서 합성 데이터를 20행씩 40개 묶음으로 나눠 비교한 결과, 신규 등록 SQL 처리 시간의 중앙값이 약 261ms에서 16ms로 줄었습니다. 기능 시험에서는 변경 전후의 저장 결과를 대조하면서 같은 항목을 반복 수정할 때 동작이 달라지는 조건도 확인했습니다.

서버를 거쳐 여러 파일을 내려받을 때는 한 파일에 오류가 나면 전체 작업이 멈췄습니다. 실패한 파일을 건너뛰고 나머지를 계속 받도록 바꿨으며, 모든 파일의 처리가 끝나면 다운로드 버튼을 다시 쓸 수 있게 했습니다.

03 범위를 먼저 정하고, 요청 흐름과 예외 상황을 그려 설계합니다

영향 범위가 큰 기능을 맡을 때는 사용자가 어떤 일을 끝낼 수 있어야 하는지부터 정리하고, 구현과 테스트에 드는 시간을 따져 이번에 꼭 구현해야 할 동작과 나중에 추가해도 되는 항목을 나눴습니다.

범위를 정한 뒤에는 화면에서 보낸 요청이 서버와 장치를 거쳐 돌아오는 과정을 흐름도로 그렸으며, DB에 저장됐는데 장치 응답이 늦는 경우까지 고려해 화면을 언제 갱신하고 다음 작업을 허용할지 정했습니다. 오디오 입력 등록을 시험할 때는 일부러 저장 도중에 실패하도록 해 DB에 어떤 값이 남는지, 화면에서 후속 등록을 멈추는지 함께 확인했습니다.

Identity

제한된 자원에서 체감 속도를 높이는 개발자

인터엠에서 임베디드 Linux 기반 오디오 장치의 웹 서비스를 개발했습니다. 한 장치에서 웹 요청과 장치 제어가 CPU와 메모리를 함께 사용합니다. 기능이 정상적으로 동작하는 상황에서도 자원 사용에 여유가 있는지, 고객이 화면에서 얼마나 기다리는지 살피게 된 이유입니다.

실제 장치에 조회 요청을 보내 HTTP 응답 시간을 확인하고, 같은 구간의 Apache 프로세스 CPU 시간과 메모리 사용량(RSS)을 기록했습니다. 화면 응답이 늦을 때 어디부터 봐야 할지 판단할 수 있도록 서버 처리와 브라우저 동작을 구분해 살폈습니다.

장치 초기화 흐름에서는 명령 간격을 유지하면서, 브라우저가 대기 중에도 다른 작업을 처리할 수 있게 바꿔 봤습니다. Playwright와 CDP를 이용한 격리 시험에서 초기화 완료까지 걸린 시간은 조금 늘었고, 화면 작업이 시작되기까지의 대기 시간은 줄었습니다. 고객이 기다리는 구간을 따로 봐야 드러나는 차이였습니다.

앞으로도 고객이 자주 하는 작업에서 병목을 찾고, 같은 조건에서 응답 시간과 자원 사용의 변화를 확인하겠습니다. 임베디드 환경에서 쌓은 경험을 바탕으로, 제한된 자원을 효율적으로 쓰면서 고객이 변화를 체감할 수 있는 서비스를 만들고 싶습니다.

    function saveConfig($_post) {


    if (!class_exists('SQLite3') || !file_exists(Isd_Mqtt\Def\CONF_PATH)) return false;


    $columns = array_keys($this->config);


    $db = null;


    $transaction = false;


    try {


        $db = new \SQLite3(Isd_Mqtt\Def\CONF_PATH, SQLITE3_OPEN_READWRITE);


        if (!$db->exec('BEGIN IMMEDIATE')) throw new \Exception('begin_failed');


        $transaction = true;


        if ((int)$db->querySingle('SELECT COUNT(*) FROM ' . Isd_Mqtt\Def\CONF_TABLE_NAME . ' WHERE f_no = 1') !== 1) throw new \Exception('config_row_missing');


        foreach ($columns as $col) {


            if (!array_key_exists($col, $_post)) continue;


            $stmt = $db->prepare('UPDATE ' . Isd_Mqtt\Def\CONF_TABLE_NAME . ' SET ' . $col . ' = :val WHERE f_no = 1');


            if ($stmt === false) throw new \Exception('prepare_failed');


            if (!$stmt->bindValue(':val', (string)$_post[$col], SQLITE3_TEXT)) throw new \Exception('bind_failed');


            $result = $stmt->execute();


            if ($result === false) throw new \Exception('execute_failed');


            $result->finalize();


            $stmt->close();


        }


        if (!$db->exec('COMMIT')) throw new \Exception('commit_failed');


        $transaction = false;


        $db->close();


        $this->config = $this->loadConfig();


        return true;


    } catch (\Exception $e) {


        if ($db !== null) {


            if ($transaction) $db->exec('ROLLBACK');


            $db->close();


        }


        return false;


    }


}

    function parse_ext_data($_common_data) {

    if ($data_length === 0) return false;


    $ext_header = array();


    $offset = 0;


    while ($offset < $data_length) {


        $remaining = $data_length - $offset;


        if ($remaining < 8) return false;


        $fields = unpack('l1tag/l1length', substr($_common_data, $offset, 8));


        $length = $fields['length'];


        if ($length < 0 || $length > $remaining - 8) return false;


        $ext_header[] = array(


            'tag' => $fields['tag'],


            'length' => $length,


            'value' => $length === 0 ? null : substr($_common_data, $offset + 8, $length)


        );


        $offset += 8 + $length;


    }


    return $ext_header;


}

    function jsonStoreUpdate($path, $mutate, $afterRead = null, $fault = null) {


    if (is_link($path)) return array('ok'=>false,'error'=>'symlink_path');


    if (is_link($path . '.lock') || is_dir($path . '.lock')) return array('ok'=>false,'error'=>'lock_open');


    $lock = @fopen($path . '.lock', 'c+');


    if ($lock === false) return array('ok'=>false,'error'=>'lock_open');


    $temp = null; $stream = null;


    try {


        if (!flock($lock, LOCK_EX)) return array('ok'=>false,'error'=>'lock_acquire');


        $bytes = @file_get_contents($path);


        if ($bytes === false) return array('ok'=>false,'error'=>'read_failed');


        $doc = json_decode($bytes);


        if (json_last_error() !== JSON_ERROR_NONE || !is_object($doc))


            return array('ok'=>false,'error'=>'invalid_json_object');


        if ($afterRead !== null) call_user_func($afterRead);


        try { call_user_func($mutate, $doc); }


        catch (Exception $error) { return array('ok'=>false,'error'=>'mutation_failed'); }


        $payload = json_encode($doc, JSON_PRETTY_PRINT|JSON_UNESCAPED_UNICODE|JSON_UNESCAPED_SLASHES);


        if ($payload === false) return array('ok'=>false,'error'=>'encode_failed');


        $temp = tempnam(dirname($path), '.isls-json-');


        if ($temp === false || realpath(dirname($temp)) !== realpath(dirname($path)))


            return array('ok'=>false,'error'=>'temp_create');


        $stream = @fopen($temp, 'wb');


        if ($stream === false) return array('ok'=>false,'error'=>'temp_open');


        $written = 0; $total = strlen($payload);


        while ($written < $total) {


            $n = ($fault === 'write') ? false : fwrite($stream, substr($payload, $written));


            if ($n === false || $n === 0) return array('ok'=>false,'error'=>'write_failed');


            $written += $n;


        if (!fflush($stream)) return array('ok'=>false,'error'=>'flush_failed');


        fclose($stream); $stream = null;


        $mode = fileperms($path);


        if ($mode !== false && !chmod($temp, $mode & 0777))


            return array('ok'=>false,'error'=>'permission_failed');


        if ($fault === 'rename' || !rename($temp, $path))


            return array('ok'=>false,'error'=>'rename_failed');


        $temp = null;


        return array('ok'=>true,'error'=>null,'bytes'=>$written);


    } finally {


        if (is_resource($stream)) fclose($stream);


        if (is_string($temp) && is_file($temp)) unlink($temp);

    }

    배경

    여러 설정 행을 한 번에 변경하는 작업은 전부 반영하거나 실패 시 전부 취소돼야 합니다. 요청마다 DB 연결을 새로 만드는 중계 구조에서 BEGIN과 COMMIT이 실제로 같은 트랜잭션에 속하는지 분석했습니다.

    문제 분석

    기존 공용 함수는 호출마다 SQLite 연결을 열고 닫았습니다. 별도 요청으로 BEGIN, UPDATE, COMMIT을 보내면 SQL 문자열은 그럴듯해도 하나의 트랜잭션이 이어지지 않습니다.

    기존 동작 재현 · 구조 분석

    판단과 검증 과정

    BEGIN과 COMMIT이 코드에 있다는 사실보다 어느 연결이 실행하는지를 확인했습니다. 호출마다 연결이 닫히면 SQL 순서가 맞아도 여러 변경을 하나의 저장 작업으로 묶을 수 없기 때문입니다.

    4. 서비스 적용 판단
    5. 화면 결과 표시

    문제 분석

    인증서로 네트워크 접근을 인증하는 EAP-TLS가 활성화된 분기에서 기존 저장값을 해석하기 전에 키를 검사하는 순서를 확인했습니다. 웹 HTTPS 인증서와 네트워크 접근 인증은 목적과 적용 프로세스가 달라 서로의 검증을 대신하지 않습니다.

    격리 개선 · 검증

    판단과 검증 과정

    기존 암호를 유지한다는 화면 표식과 실제 암호는 다른 값입니다. 저장값을 먼저 해석한 뒤 키를 검사하도록 순서를 조정했으며 검사 기준은 완화하지 않았습니다. 키·명령·설정 적용은 시험용 대체 경계로 분리해 실제 네트워크 연결을 변경하지 않았습니다.

    처리 흐름

    1. 접근 인증 방식 선택
    2. 기존 값 유지·새 입력 구분
    3. 서버 키 검사
    4. 설정 파일
    5. 인증 프로세스
    6. 상태 재조회

    구현과 설계 판단

    저장값 해석을 키 검사 앞으로 이동한 코드를 검증했습니다. 키는 시험 중 RAM에서만 생성하고 설정 쓰기·shell·대기는 시험용 함수로 교체해 실제 네트워크 적용을 피했습니다.

    기존 값 유지 표식과 실제 키 암호의 차이
    검사를 완화하지 않고 순서를 조정

    화면의 유지 표시값은 실제 암호가 아닙니다. 기존 저장값으로 해석하기 전에 키를 검사하면 유지 요청도 실패할 수 있어 해석을 먼저 하도록 한 분기만 바꿨습니다.

    검사에는 실제 라이브러리, 설정에는 대역

    시험용 키는 메모리에서 만들고 실제 OpenSSL로 확인했습니다. 설정 쓰기와 명령 실행은 대체해 실제 네트워크 인증을 바꾸지 않았습니다. 이 결과는 키 검사 순서에 관한 것이며 인증서 쌍·신뢰 체인·실제 망 인증의 성공 결과는 아닙니다.

    배경

    웹에서 장치의 날짜·시간대와 NTP 시간 서버 동기화 정책을 설정합니다. 입력값 검증, 설정 파일 저장과 운영체제·하드웨어 시계 반영은 서로 다른 단계입니다.

    문제 분석

    시각을 입력하고 시간대를 변환한 뒤 공용 JSON에 저장해 장치 측 프로세스에 적용하는 순서를 연결했습니다. 일정 기능과 구분해 시스템 시계 설정만 다룹니다. NTP 설정 API의 허용 값 검사와 공유 읽기·수정·쓰기 잠금도 서로 다른 계약입니다.

    문제 분석

    모드 선택이 환경 설정인 env와 JSON을 따로 바꾸는 흐름을 추적했습니다. 파일 존재 확인이 유효한 JSON이나 실제 환경 일치까지 보장하는 것은 아니며 코드의 대체 처리 경로인 fallback과 실제 부팅 호출 코드를 연결해야 했습니다.

    기존 구조 분석

    판단과 검증 과정

    메뉴가 새 모드로 바뀌어도 부팅 때 다른 파일을 읽으면 다시 옛 동작으로 돌아갈 수 있습니다. 화면 선택이 환경 파일·JSON·메뉴·기동 호출에 전달되는 순서를 추적했습니다. 파일 존재와 유효한 내용, 복수 파일의 일관성을 나눠 살폈으며 실제 부팅 전환 성공은 측정하지 않았습니다.

    처리 흐름

    1. 동작 모드 선택
    2. 관련 설정 파일 갱신
    3. 메뉴·서비스 구성
    4. 다음 기동 시 같은 모드 반영

    구현과 설계 판단

    모드값이 없을 때 기본 모드를 선택하고 환경 파일이 없으면 기존 설정을 유지하는 동작을 추적했습니다. 메뉴 구성과 기동 호출 코드에서 같은 모드가 전달되는지 구조를 대조했습니다.

    기존 코드에 호환성 검사를 먼저 적용한 뒤 AI에게 수정을 맡겼습니다. 처음부터 코드 전체를 무조건 변환하기보다 사전 검사에서 드러난 항목을 출발점으로 삼았습니다.

    테스트할 조건도 작업에 포함

    AI에는 문법 변경만 요청하지 않았습니다. 기존 버전에서는 드러나지 않던 문제가 새 버전에서 나타날 수 있는 조건을 실행하고, 프론트엔드 동작과 백엔드 처리도 하나씩 확인하도록 요청했습니다. CDP로 브라우저 동작과 실행 상태를 확인했습니다.

    실행 오류를 다음 수정의 입력으로 사용

    Fatal 오류처럼 해당 코드를 실행해야 확인할 수 있는 문제까지 수정 대상으로 삼았습니다. 수정 뒤 같은 조건을 다시 실행하도록 해, 코드 변경에서 테스트까지 이어지는 반복 작업에 AI를 활용했습니다.
